# DSH 开放网页评测 Pipeline

## 目标

构建一套**面向长轨迹智能体的提示约束指令遵循评测数据集**。任务应让智能体经历有依赖的多个步骤，例如先查明产品型号，再去另一来源检索该型号的规格，最后合并证据并作答。提示约束考察智能体能否在这些步骤中持续遵守工具顺序、证据使用或中间产物要求。判断轨迹是否有足够复杂度，要看后一步是否依赖前一步的发现、是否需要核验或合并来源，以及约束是否在关键步骤反复适用。工具调用次数用于辅助诊断。

数据集以**同一道原题及其约束变体**为分组单位。一个可评测样本需关联原题及来源、约束文本及版本、可执行判定规则、独立会话的轨迹和证据产物，以及任务正确性的参考依据。答案是否正确与约束是否遵循分别判定，两项都达标才记为联合成功。

本目录是购物、医疗健康和社会民生三类任务的开放网页实现，覆盖固定题目、注入已定义约束、采集轨迹和评分。当前约束是共有的证据记录与抓取顺序规则，适用于单次会话中的多步工具交互。要求约束跨用户回合或跨会话持续生效的题型，需要额外的回合与状态设计。

## 流程

完整的构建顺序是**筛选候选题 → 用开发基线设计约束 → 锁定规则并配对运行 → 双维度评分 → 验收入库**。下面逐步说明每一步的产物与缺口。现有命令从已筛选的清单和预置规则开始。开发基线复盘、约束设计与正式入库仍需人工完成。

### 1. 筛选能形成长轨迹的原题并固定来源

- **为什么这样做** 同一道题的措辞、返回格式或来源口径一旦变化，条件间的差异就可能来自题面本身。筛选时优先找检索链有依赖、需要跨来源核验或有多个条件要合并的题目。保留筛选后的 DeepSearchQA 原题，并固定上游版本。
- **能得到什么** 题目清单记录原始行号、类别、题面及哈希。运行前校验清单，使用 `assess.py --reference` 还能把每题与固定版本 CSV 逐字核对。参考答案由评分器单独读取。 [题目清单](user_query_openweb_246.jsonl) · [输入校验](common.py)
- **还差什么** 当前流程从已选题目开始。题目的多步检索难度、来源分布和各类覆盖仍需在入库前审查。核对题面与上游一致可以追溯来源，网页上的证据和参考答案是否仍然有效需要另行复核。

### 2. 用开发基线定位值得约束的行为

- **为什么这样做** 先用 DSH 在开发题上运行原题，观察智能体如何搜索、抓取、核验和写入。约束应对应轨迹中可见的行为，并保留完成原题的可行路径。例如，若抓取前缺少可追溯的 URL 来源，可以要求链接先出现在原题或已完成的搜索结果中。
- **能得到什么** 一条候选规则、能定位的基线事件、满足规则的替代路径，以及用轨迹或产物判定规则的条件。规则锁定后，用独立会话重新运行同批次 S0，作为带约束条件的对照。
- **还差什么** 当前执行脚本读取已有规则。开发轨迹的归纳、可行路径复核和提示措辞仍靠人工。扩充数据时需要按原题及近重复题分开发、验证和保留测试集，避免用同一批题调规则再估计评测表现。

### 3. 把检索约束拆成三种条件

- **为什么这样做** 分别引入证据记录和检索顺序要求，便于观察新增要求对应的行为变化。
- **能得到什么** S0 使用原始系统提示。S1 要求先成功抓取至少两个不同网页，再在作答前用 `write` 把每个网页的 `url`、`role` 和 `scope` 写入 `evidence_check.json`。S2 在 S1 基础上，要求每次抓取的 URL 已经出现在原题或此前完成的搜索结果中。三种条件的提示均写入 `policies.json`。 [条件定义](policies.py)
- **还差什么** 现有规则覆盖证据记录和抓取顺序。若要考察长轨迹中更持续的指令遵循，还需设计跨多个检索分支生效的约束，并核查约束是否有足够的触发机会。当前条件设计可以比较 S1 相对 S0 的变化，以及已要求记录证据时 S2 相对 S1 的变化。若要估计顺序要求单独使用的影响，需要补充仅含该要求的条件。

### 4. 为每道题生成配对调度

- **为什么这样做** 让每道题进入所有条件，可以按同一题对照执行情况。用固定种子打乱题目和题内条件的提交顺序，减少某个条件总是先启动带来的顺序偏差。
- **能得到什么** `schedule.json` 记录题目与条件组合、提交顺序、随机种子和运行参数。`--plan` 可在发起 API 调用前检查调度。 [调度入口](run.py)
- **还差什么** 提交顺序可复现，实际并发和服务响应随负载变化。当前每题每条件各运行一次，估计运行间波动需重复执行，并记录各批次的服务配置和运行时间。

### 5. 运行 DSH 并保留原始轨迹

- **为什么这样做** 给每个会话独立工作目录，避免不同条件共享证据文件。把原题放在标准输入、把约束放在系统提示，可保持各条件的题面一致。
- **能得到什么** 各会话使用相同的模型、网页工具和超时设置。工具事件、最终回答及诊断分别保存在 `events.jsonl`、`final.txt`、`diagnostics.log`。尝试索引记录执行状态与题面哈希，可以回查超时、空回答和工具错误。 [运行器](run.py) · [运行配置](patches/)
- **还差什么** 实时网页可能变动、限流或拒绝抓取，搜索结果也会随时间变化。需要可复现证据时，要另行保存网页与搜索结果快照，并记录抓取时间和内容哈希。

### 6. 根据事件验证指令遵循

- **为什么这样做** 约束要求的是实际行为与先后顺序。使用工具请求、完成事件和最终落盘文件，可以核实抓取与写入是否真实发生。
- **能得到什么** S1 检查至少两个不同 URL、三个字段均非空、抓取先于写入、写入完成先于作答，并核对文件与写入内容。S2 额外逐次检查抓取请求发出前 URL 是否已可见。S0 标记为不适用，S1 和 S2 在没有正常最终回答时标记为不可判定。 [事件解析](dsh_events.py) · [评分规则](assess.py)
- **还差什么** 抓取成功依赖事件状态、HTTP 响应和拦截页识别，只能近似识别可用正文。`role` 和 `scope` 的真实性、证据与结论是否匹配，仍需另做语义核验。跨网站重定向和等价 URL 也可能需要补充判例。

### 7. 单独评估最终答案（可选）

- **为什么这样做** 约束执行情况与答案是否正确是两个指标。独立评分调用只根据原题、参考答案、答案类型及最终回答判断内容是否正确。
- **能得到什么** 开启 `--judge` 后，评分器对正常最终回答返回完全正确、部分正确、错误或不可判定。未启用评分网关、回答缺失或评分接口失败时，答案正确性保留为不可判定，并记录原因。 [答案评分](assess.py)
- **还差什么** 评分模型可能误判同义表达、集合答案和存在歧义的题目，固定参考答案也可能随网页更新而失效。需要对争议样本进行人工复核，建立可反复检验的评分样例。

### 8. 汇总并定位问题

- **为什么这样做** 单看已完成的会话会遗漏超时和不可判定的尝试。保留完整分母，可以区分执行失败、约束失败和答案错误。
- **能得到什么** `assessment.jsonl` 保存逐次评分、诊断和事件文件哈希，`assessment_summary.json` 按条件与类别汇总。联合成功要求正常完成、答案完全正确，并且适用的约束通过。
- **还差什么** 当前汇总提供计数。需要分析约束影响时，还应按同题的条件变化做配对分析，对重复运行估计不确定性，并核查不同条件下的基础设施故障是否集中出现。

### 9. 验收样本并归档版本

- **为什么这样做** 一次运行产生的是构造证据。正式入库前需要核实题目可解、约束确实触发、评分能够复核，并检查作答所需信息未被约束改变。
- **能得到什么** 按原题关联题目、规则、配对会话、轨迹哈希和双维度评分。正式样本应有独立复核为正确的基线，以及至少一次同时遵循规则且正确作答的变体，用来证明可行性。证据不足或需改写规则的候选保留处理记录，便于迭代。
- **还差什么** 当前目录提供会话级产物。正式发布还需要样本验收表、开发与测试划分、规则修订记录、失败样本的处理依据，以及按能力覆盖检查数据集版本。

## 调用接口

在本目录执行。每个 `--output` 需要一个尚未创建的目录。

```bash
# 生成调度，无需 DSH 或网关
python3 run.py --output ./runs/plan --plan

# 配置网关后运行，参数值可按部署调整
python3 run.py --output ./runs/openweb --profile headless \
  --workers 15 --timeout 390 --seed 246118

# 根据工具轨迹和证据文件评分
python3 assess.py ./runs/openweb

# 如需同时评估答案正确性，设置评分网关后执行
python3 assess.py ./runs/openweb --reference /path/to/DSQA-full.csv --judge
```

| 入口 | 参数与产物 |
| --- | --- |
| `run.py` | `--profile` 选 DSH profile，`--dsh` 选可执行文件，`--workers` 控制并发，`--timeout` 以秒计，`--seed` 固定调度。生成 `schedule.json` 和 `policies.json`。实际运行还生成 `attempt_index.jsonl`、`run_summary.json` 及各会话工作目录。 |
| `assess.py` | 接收已完成的运行目录。默认执行轨迹评分，`--judge` 打开答案评分并要求 `--reference`，`--workers` 控制评分并发。生成或更新 `assessment.jsonl` 和 `assessment_summary.json`。只传 `--reference` 可校验参考快照及题面。 |

运行环境为 Linux、Python 3.9+、GNU `timeout` 和 DSH。DSH profile 需加载 headless 工具并能解析 `@deepseek-ai/dsh-web-search-serper`。参考 CSV 取自 `common.py` 指定的 DeepSearchQA 版本。 [固定版本 CSV](https://huggingface.co/datasets/google/deepsearchqa/resolve/b2623f8653065c2672de6d941fc5434cd652376c/DSQA-full.csv)

| 配置 | 环境变量 |
| --- | --- |
| DSH | `DSH_HOME` 可指向已配置 profile 的目录，`DSH_BIN` 可指定可执行文件 |
| 答题模型 | `COMPANY_DEEPSEEK_BASE_URL`（OpenAI 兼容基址，通常以 `/v1` 结尾）、`COMPANY_DEEPSEEK_API_KEY` |
| 网页搜索 | `SERPER_BASE_URL`、`SERPER_API_KEY`、`SERPER_AUTH_MODE`（默认 `bearer`） |
| 答案评分 | `OPENWEB_JUDGE_URL`（完整的 `/v1/chat/completions` 地址）、`OPENWEB_JUDGE_API_KEY`，启用 `--judge` 时使用 |

## 维护方式

| 变更 | 修改位置和检查 |
| --- | --- |
| 增删题目或更新来源 | 更新题目清单及 [common.py](common.py) 中的版本、哈希和数量校验。保留已有题目的来源 ID，更新行号和题面哈希后用 `--reference` 核对原文，再用 `--plan` 检查每题的条件覆盖。 |
| 修改条件或新增约束 | 同步更新 [policies.py](policies.py) 的提示文本和 [assess.py](assess.py) 的评分规则。条件集合有变化时同步调整 `common.py`，用通过、违规和缺少最终回答的轨迹检查判定。 |
| 更换模型、搜索服务或 DSH 版本 | 更新 [patches](patches/) 中的模型和网页配置。模型 ID 变化时同步核对运行元数据与评分模型配置。DSH 事件格式有变化时更新 [dsh_events.py](dsh_events.py)，用典型轨迹检查搜索、抓取、写入和最终回答的解析。 |
| 更新数据集版本 | 按原题组维护开发、验证和保留测试划分。更新题目与规则版本、轨迹及评分索引，核对每个正式样本的入库依据和评测能力覆盖。 |
| 归档一次运行 | 使用独立目录保存调度、条件文本、尝试索引和评分产物。模型与搜索凭证通过环境变量提供，参考答案和原始会话轨迹保存在运行环境。 |
