# SWE-bench / SWE-agent / Agentless 对真实仓库修复任务的评测对比

先厘清一个结构性前提：这三者不是同类可平行比较的"三个基准"。**SWE-bench 是评测框架（数据集 + 判分协议）**，而 **SWE-agent 和 Agentless 是两种解决真实仓库修复任务的"方法/系统"，恰好都在 SWE-bench 上被评测**。因此下面把"样本与环境、成功率口径、轨迹、复现性"拆开时，SWE-bench 提供的是"基准侧"定义，SWE-agent 与 Agentless 提供的是"方法侧"各自怎么用、怎么偏这个口径。

---

## 一、样本与环境

| 维度 | SWE-bench（基准论文，2023） | SWE-agent（2024） | Agentless（2024） |
|---|---|---|---|
| 定位 | 评测框架 / 数据集 | 代理方法（ACI 抽象层） | 无代理三阶段管线 |
| 样本 | 2,294 实例，12 个 Python 仓库（django/sympy/sklearn/sphinx/pytest…）；由 ~93,139 个 PR 经三阶段过滤而来 | 复用在 SWE-bench 上评测：主结果在**全量 2,294**，消融在 **SWE-bench Lite（300）** | 主要在 **SWE-bench Lite（300）**；另构造 **Lite-S（249）**，并自评 **SWE-bench Verified（500）** |
| 单实例构成 | issue 文本 + 基线 commit 代码库 + gold patch + test patch + FAIL_TO_PASS / PASS_TO_PASS 测试清单 | 同 SWE-bench；agent 在容器里多轮交互后由最终代码状态自动生成 patch | 同 SWE-bench 的 issue + 代码库；自己重做定位/修复/验证，最终产出 diff 提交 |
| 执行环境 | 每仓库按版本建 **conda 环境**；用**仓库镜像 + base commit** 固定代码库 | **Docker 容器**（沿用 InterCode 的交互环境），容器隔离推理与评测 | 复用官方评测框架但**改写评测脚本**以自由执行回归/复现测试 |
| 模型 / 预算 | Claude 2、GPT-4（32k）、ChatGPT-3.5、SWE-Llama 7b/13b；单次生成、无多轮预算 | GPT-4 Turbo / Claude 3 Opus；**单实例预算 $4**（超预算自动提交当前编辑） | GPT-4o（gpt-4o-2024-05-13）；平均成本 $0.70 |

要点：SWE-bench 的"样本"是**真实的 GitHub issue→合并 PR**，用"该 PR 贡献了测试改动 + 存在 fail→pass 测试"来保证可验证，这是三者共同的样本来源；SWE-agent 与 Agentless 的区别不在样本，而在**拿同一批样本时怎么解题**。

## 二、补丁成功率的口径（这是三者最需要警惕的差异）

**SWE-bench 定义的官方口径**（§A.4）：
- 判"解决（Resolved）"必须同时满足：patch 能应用**且** `FAIL_TO_PASS` **和** `PASS_TO_PASS` **两组测试全部通过**（缺一个或非 pass 都算 fail）。
- 它同时报告 `% Apply`（patch 仅"能打上"）和 `% Resolved`（能打上且全测过）。二者差距巨大（例如 Claude 2 oracle：Apply 47.00% vs Resolved 4.80%）。**引用成功率时，"能打上补丁"和"真正解决"是两个口径**，混用会严重高估。
- 另有一个易被忽略的宽松点：评估里对打不上的 patch 有一步**自动修复**（删多余上下文行、重算 header），所以 `% Apply` 本身也不是"原始 patch 直接可用"。

**SWE-agent 的口径**：沿用 SWE-bench 官方 `% Resolved / pass@1`（"生成 patch 应用后全部测试通过的比例"），与基准口径**一致**，但多报了一个 `Avg. $ Cost`。

**Agentless 的口径（关键偏离）**：
- 它**没有**使用 SWE-bench 官方缓存的 `PASS_TO_PASS` 回归集，而是**自己在原仓库跑一遍测试、再用 LLM 挑出"可能随修复被改动"的测试排除**，得到自定义回归集；再叠加自己生成的复现测试来选补丁。
- 论文脚注 1 直接承认：**"若直接使用官方 PASS_TO_PASS，SWE-bench Lite 上是 98（而非 96）"**。也就是说它的 32.00% 是"自己的回归口径"下的数字，与官方口径不严格可比——这正解释了后来为什么要有 SWE-bench Verified 统一口径。

> 结论：比较成功率时，SWE-bench 的 `% Resolved` 是"全测过"口径，SWE-agent 沿用它，Agentless 用的是**自定义回归集 + 生成复现测试**的口径，三者不可直接放同一行比。

## 三、可观测轨迹（可查看 ≠ 已定义合规打分）

| | SWE-bench | SWE-agent | Agentless |
|---|---|---|---|
| 是否有过程轨迹 | **无**——基线是检索 + 单次生成 patch，无中间推理可看 | **有**，多轮 thought+action+observation，存成 `.traj`，逐轮可见 | **无代理轨迹**——但保留结构化中间产物（定位集合、候选补丁、复现测试、回归集、最终排序） |
| 可观测到 | 只有最终 patch 与测试日志 | 每步命令、观测、编辑、失败编辑、提交；附失败模式自动分类（GPT-4o 标注 9 类，与人一致率 87%） | 各阶段的输入/输出产物，可静态回溯 |
| 轨迹工具 | — | 开源轨迹 + 轨迹查看器（`inspector`，见仓库文档，非论文正文） | — |

这是三者最鲜明的差别：**SWE-agent 是三家里唯一"过程完全可观测"的**（这也是它论文 5.2 节能做大量行为分析的原因）；SWE-bench 完全没有过程；Agentless 有产物但没有"决策循环"，因此不是"轨迹"而是"中间结果链"。

## 四、可复现性

- **SWE-bench**：开源数据（2,294 实例 JSON）+ 评测代码 + 仓库镜像（防止原仓库 base commit 变动导致实例失效）；conda 环境 + 缓存测试结果。复现性最好的一面是"执行式验证"本身可重跑。
- **SWE-agent**：开源代码、配置文件（.yaml 定义 ACI）、Docker 容器保证环境可复现；论文 E.2 声明**开源了轨迹、代码生成、评测执行 trace、分析 notebook**，称结果"可完全从数据渲染出来"。是三家里对"过程复现"承诺最强的一个。
- **Agentless**：开源代码（OpenAutoCoder/Agentless），但用的是闭源模型 GPT-4o，且**改写评测脚本、自选回归测试**，复现时若不照它的口径，数字会对不上（96 vs 98 即一例）。论文"内部效度"一节也承认 GPT-4o 训练数据可能含 gold patch 的泄漏风险。

## 五、论文实际报告的结果（事实，务必区分数据划分/模型/版本/预算）

**SWE-bench（2023，v1，全量 2,294）**——`% Resolved`：

| 模型 | BM25 | Oracle 检索 |
|---|---|---|
| ChatGPT-3.5 | 0.20% | 0.52% |
| Claude 2 | 1.96% | **4.80%** |
| GPT-4（仅 25% 子集） | 0.00% | 1.74% |
| SWE-Llama 7b | 0.70% | 3.00% |
| SWE-Llama 13b | 0.70% | 4.00% |

**SWE-agent（GPT-4 Turbo / Claude 3 Opus）**：

| 数据集 | GPT-4 Turbo | Claude 3 Opus |
|---|---|---|
| SWE-bench 全量 | **12.47%**（286/2294，$1.59） | 10.46%（$2.59） |
| SWE-bench Lite | **18.00%**（54/300） | 13.00% |
| 参考：Shell-only（Lite） | 11.00% | — |
| 参考：RAG（Lite） | 2.67% | 4.33% |
| HumanEvalFix pass@1 | 87.7%（Py） | — |

**Agentless（GPT-4o）**：

| 数据集 | 结果 | 位置 |
|---|---|---|
| SWE-bench Lite（300） | **32.00%**（96/300，$0.70） | **开源方法里最高**；但闭源 CodeStory Aide 达 43.00%，故"不是全场最高" |
| SWE-bench Lite-S（249） | 33.73%（84/249） | 排名第 9 |
| SWE-bench Verified（500） | 38.80%（194/500） | GPT-4o 口径下最佳 |

> 引用这些数字时必须带上"哪个数据划分 + 哪个模型版本 + 预算多少"：同样是"SWE-agent"，GPT-4 Turbo 在全量是 12.47%，在 Lite 是 18.00%；同样"Claude"，SWE-agent 的 Claude 3 Opus 是 10.46%，而 SWE-bench 论文里的 Claude 2 只有 1.96%。混为一谈会制造数倍的偏差。

## 六、我的轨迹合规评测建议（以下为我提出的评测设计，**非论文已报告内容**）

这里回应资料索引里那句关键区分：**"轨迹可查看"和"已定义合规打分"是两件不同的事**。三篇论文的状态是：

- SWE-agent 做到了"**轨迹可查看**"（开源 `.traj` + inspector），但**没有定义合规打分**——它的失败模式分类是事后描述性标注，不是"这条轨迹是否合规/补丁是否可从轨迹因果还原"的审计。
- Agentless 反而用自己的实践印证了这个缺口：它明确指出多数闭源工具"**不提供任何轨迹，只给提交补丁，因此无法核验其步骤**"；但它自己也没给出"中间产物可回放 + 可自动合规打分"的机制。
- SWE-bench 完全不评轨迹，只评最终补丁的测试结果。

**我建议补一套"轨迹合规评测"，把"能看轨迹"升级为"能自动判定轨迹合规"**，至少五条可机检的维度：

1. **补丁—轨迹因果可溯源（provenance）**：最终提交 patch 必须能从轨迹中记录的编辑动作无损重建；凡最终 diff 里出现轨迹中不存在的改动，判为"无来源修改"违规。这把"补丁成功"从"测试过了"升级为"补丁确实由这条轨迹产生"。
2. **越界 / 泄漏审计（contamination audit）**：轨迹中不得出现读取 gold patch、test patch、FAIL_TO_PASS 隐藏测试，或读取 PASS_TO_PASS 之外未公开测试的动作；对 Agentless 类方法则要核验它没把官方 PASS_TO_PASS 当作选择依据（它自己已声明不用，合规打分应能自动验证这一点）。
3. **环境与预算合规（environment/budget conformance）**：每步动作在声明的容器/环境内执行、上下文窗口与成本在声明阈值内、无未申报的外部工具越权。
4. **可回放性（replay determinism）**：给定相同模型版本 + 温度 + 环境种子，轨迹应可逐步回放复现到同一 patch；所有非确定性来源（采样温度、模型快照、时间戳）必须显式记录，否则判"不可复现"。
5. **方法一致性（method conformance）**：Agentless 类声称"无 LLM 自主决策"，合规检查应自动验证每个阶段产物确实由声明的阶段产生（定位→修复→验证），没有隐藏的代理循环；SWE-agent 类则验证"thought→action→observation"循环未被外部捷径绕过。

这样做的意义：把评测从"**只信最终测试结果**"（SWE-bench 的唯一判据，容易被口径漂移或泄漏钻空子）扩展到"**同时审计求解过程是否合规、补丁是否可归因**"，从而让"32.00% vs 12.47% vs 4.80%"这类跨方法对比在**同一轨迹合规基线上**才有真正可比性——而这一点，三篇论文目前都还没有做到。

---

**一句话总结**：SWE-bench 给出"真实样本 + 全测过的解决率口径"但无过程；SWE-agent 提供了最完整的过程轨迹与容器化复现、口径与基准一致；Agentless 以无代理管线在 Lite 上拿到开源最高 32.00%、但用了自定义回归口径（官方口径下是 98 不是 96）；三者"成功率不可裸比"，且"轨迹能看"不等于"轨迹已按合规标准打分"——后者是我建议新增的评测维度，而非论文已报告的结论。

需要的话，我可以把第六节的"轨迹合规评测"落成一份可执行的评分 rubric（含每条维度的判定规则、违规样例与通过/失败判据）。
